# bili-clip

把一场直播回放变成几条可发的切片。脚本负责确定性的活（拉数据、切视频），你负责读稿、挑片、起标题、和切片员对话。

脚本路径：`<本 skill 目录>/scripts/bili_clip.py`，下文简写为 `bili_clip.py`。所有子命令都支持 `--help`。

## 依赖与首次配置

| 依赖 | 用途 | 缺失时 |
|------|------|--------|
| python3 ≥ 3.10 | 跑脚本 | 提示安装 |
| yt-dlp | 导出浏览器 cookie、下载视频 | `brew install yt-dlp` |
| ffmpeg（带 libass） | 切片、封面截图、把弹幕烧进画面 | `brew install ffmpeg-full`（Homebrew 的 `ffmpeg` 是精简版，没有 libass，切不带弹幕的没问题，`--danmaku` 会报错） |
| biliup（可选） | 投稿 | 只有用户要发布时才提示，见「发布」 |

登录态：AI 字幕必须登录才能拉。脚本首次运行会自动 `yt-dlp --cookies-from-browser chrome` 导出到 `~/.config/bili-clip/cookies.txt`（macOS 首次会弹钥匙串授权，让用户点允许）。失败时告诉用户两条路：换浏览器 `bili_clip.py cookies --browser edge`，或用浏览器插件导出 Netscape 格式 `cookies.txt` 放到该路径。Windows 上 Chrome 新版 cookie 常读不到，直接走导出文件那条路。

目录约定：工作目录 `~/Movies/bili-clip/<BV>_<标题>/`，主播登记表 `~/.config/bili-clip/streamers.json`（机器用：uid、别名、回放列表、切过的场次），主播档案 `~/.config/bili-clip/streamers/<主播名>.md`（给你读：人物、梗、投稿模板）。可用环境变量 `BILI_CLIP_ROOT` / `BILI_CLIP_CONFIG` 改。

## 流程

### 0. 记住主播，自动拉最近一场

切片员长期盯固定主播，每天等回放。B 站 UP 主通常把回放放在一个「系列」或「合集」里（`space.bilibili.com/<uid>/lists/<id>?type=series`），每天自动追加。skill 用 `~/.config/bili-clip/streamers.json` 记住每个切过的主播和她的回放列表。

- **绑定回放列表**（每个主播一次）：用户贴系列 / 合集链接时，`parts <链接>` 或 `streamers --set-list <链接>` 都会登记到它所属的主播名下，并处理最新一集。
- **之后只要说主播名**：

```
python3 bili_clip.py latest <主播名|别名|uid>
```

它读登记表，取回放列表里最新一集，直接跑 `parts`。输出同第 1 步。最新一集上次已经切过时会停下并说明，加 `--force` 重来；`--list` 只看最近几集不建目录。

- **用户提到的名字对不上登记表**：脚本会打印 B 站用户搜索结果让你确认，或提示用 uid。用户口头叫法（「陌陌」「墨墨」）和 B 站昵称（「丝茉茉i」）常不一样，确认后用 `streamers --alias <主播名或uid> 陌陌 墨墨` 记下别名，下次就能直接叫。
- **没绑定列表的主播，第一次用先要链接，别急着猜**：向用户要她空间页的回放系列 / 合集链接（`space.bilibili.com/<uid>/lists/<id>?type=series`，B 站空间页「合集和列表」里能找到），拿到后 `streamers --set-list` 绑定再 `latest`。只有用户明确说没有链接、让你自己找时，才用 `latest` 退回到按标题关键词从最近投稿里猜——这条路不可靠：UP 主可能有多个高度同名的马甲/备份号（如「XX 的小号」和「XX 的录播小号」），最近投稿里也可能混着非回放内容或很久以前的一条，猜出来的不一定是真正按时间排的最新一场回放。猜完必须把结果（标题、时间、时长）念给用户确认，而不是直接当作「最近一次录播」往下走；用户一旦给出真正的系列链接，立刻改用它重新绑定。
- `streamers` 不带参数列出所有记住的主播、别名、回放列表和最近一场。

`parts` 每次运行都会自动登记主播和这场的工作目录，所以用过一次链接的主播也在表里，只是可能没有回放列表。

### 1. 列分 P

```
python3 bili_clip.py parts "<用户给的链接>"
```

- 输出分 P 清单：序号、时长、字幕语言（`ai-zh` 为 AI 字幕，`无` 表示还没生成）、弹幕数、标题。把这张表原样给用户看，让用户回复要分析哪些序号（`1,3-4` 或「全部」）。
- 一个 BV 多个 P 是最常见的回放形态，默认只列这个 BV 的 P。如果输出末尾提示「该视频属于合集」，只有用户明确要整个合集时才加 `--season` 重跑（合集几十集时会逐集请求，慢）。
- 直接给合集链接（`space.bilibili.com/<uid>/lists/<id>?type=season`）也可以。
- 没有 AI 字幕的 P 不能分析。告诉用户 B 站字幕生成有延迟，稍后重跑 `parts` 或 `analyze --refresh`。不做本地转写回退。
- 输出里会告诉你主播档案存不存在，记下来，第 3 步要用。

### 2. 拉数据

```
python3 bili_clip.py analyze <工作目录或BV号> --parts 1,3-4
```

每个 P 生成 `raw/pNN_compact.txt`（压缩稿）和 `raw/pNN.srt`（原始字幕），stdout 是 JSON 摘要，含每个 P 的弹幕峰值时刻。

压缩稿格式：每 30 秒一行，`[时间] (弹幕N 🔥 [高频弹幕]) 字幕内容 / 字幕内容 ...`。🔥 表示这 30 秒弹幕密度在本 P 前 5%。语气词行已去掉，`♪` 包着的是唱歌。

### 3. 分析、推荐

先判断用户要的是哪一种：

| 模式 | 触发 | 产出 |
|------|------|------|
| **定向** | 用户点名了具体片段：「切一下她唱恋爱循环那段」「纯黑迟到那里」「打 boss 全灭的那一把」 | 只定位这一处，**一个候选**（同一件事分散在几处时才多个），不推荐别的 |
| **发现** | 没给方向，或只说「看看有啥可以切的」「找找高能」 | 一场合计 6 到 8 个候选 |
| **混合** | 「唱恋爱循环那段，再帮我看看还有啥」 | 先定向，再用剩余名额发现 |

**定向模式**不要通读压缩稿。用 `find` 先定位：

```
python3 bili_clip.py find <工作目录> 恋爱循环 循环 --parts 2
```

它在字幕和弹幕里搜关键词，按 P 聚成命中区间，给出建议起止和命中样例。要点：

- 关键词多给几个同音、别名写法（ASR 会把「纯黑」写成「重黑 / 除黑」，「丝茉茉」写成「苏墨墨 / 思墨墨」），任一命中即算。人名、歌名、梗、游戏事件都可以搜。
- 弹幕命中往往比字幕更准（观众会打出歌名和梗），弹幕成堆的那一处通常就是答案。
- 拿到区间后回读该处 `raw/pNN.srt` 定精确边界，再按下面的候选格式写 `candidates.json`。用户描述得含糊、命中有多处时，把几处都列出来让用户选，不要自己猜一个。
- 没命中就换写法再搜；仍然没有，再读对应时间段的压缩稿，最后才是告诉用户没找到。

**发现模式**先读主播档案（存在的话），再逐个 P 读 `raw/pNN_compact.txt`。8 小时回放的压缩稿加起来十几万字，**一次只读一个 P**，读完把候选记在心里再读下一个，不要把所有 P 一次塞进上下文。

推荐规则：

- **发现模式一场直播合计 6 到 8 个**候选，跨所有选中的 P，不是每 P 各推。按推荐强度排序。定向模式只给用户点名的那一处。
- **单段 30 秒到 5 分钟**。超过 5 分钟的连续内容（唱整首歌、一整局对战）单独标 `"long": true`，由用户决定切不切或拆几段。
- **两个信号对齐**：字幕看主播在说什么，弹幕看观众在哪炸。🔥 块附近优先看；但直播回放的弹幕常常很稀（几百条甚至 0），弹幕为 0 时只看字幕，别硬套。
- **类型**限定为：名场面、搞笑、唱歌、互动、游戏高光、争议、感动、科普。一个候选一个类型。
- **标题**按 B 站切片风格写：主播名 + 梗或冲突点，20 字以内，可以带一个感叹或反问。不写「直播回放 P3 片段」这种无信息标题。
- **理由**一两句话，说清为什么值得切、笑点或爆点在哪。**摘录**放 1 到 3 句原字幕。
- 候选内容提到其他已登记主播时，用登记表里的规范名写入 `mentioned_streamers`；口头叫法先用 `streamers --alias` 登记，避免同名小号或录播号混淆。

定边界要回读 `raw/pNN.srt`：

- 起点放在一句完整话的开头，比压缩稿里的时间早 1 到 2 秒，让观众听到前因。
- 终点放在笑点或反应之后 1 到 3 秒，把「哈哈哈」或弹幕爆发留进去，别切在半句话上。
- 唱歌段以歌曲起止为准，前奏可以留，间奏里的闲聊看情况。

把结果写入工作目录的 `candidates.json`：

```json
{
  "candidates": [
    {
      "id": 1,
      "part": 3,
      "start": "01:12:05",
      "end": "01:14:40",
      "type": "搞笑",
      "title": "等了 20 分钟，纯黑来一句「12 点再玩吧」",
      "reason": "主播苦等联机队友，对方一句话把她整破防，弹幕刷屏。",
      "quote": "我真绷不住了 / 我等他20分钟 / 纯黑来了一句要不12点再玩吧",
      "mentioned_streamers": ["纯黑"],
      "long": false
    }
  ]
}
```

`start` / `end` 接受 `HH:MM:SS`、`MM:SS`、`1h23m10s` 或秒数。`part` 是 parts 输出里的序号。`id` 从 1 递增，后面所有交互都用它。`mentioned_streamers` 只放已在 `streamers.json` 登记的规范名，没有提到其他主播时省略。

在对话里用一张表展示候选：序号、类型、P 和时间段、时长、标题、一句理由，然后进入预览。定向模式只有一个候选时不用表，一段话说清位置和边界即可。

### 4. 预览

```
python3 bili_clip.py preview <工作目录>
```

脚本先校验 `candidates.json`（字段、时间越界、id 重复），失败会打印原因，改完重跑。通过后生成 `preview.html` 并在默认浏览器打开：每个候选一张卡片，内嵌 B 站播放器定位到起点，标注起止、时长、理由、摘录、弹幕密度分位。

每张卡片有「定位开头」「定位结尾」两个按钮：开头跳到起点开始播，结尾跳到终点前 8 秒，方便检查两头切得准不准；跳转只定位不自动播放，用户自己点播放。B 站播放器到终点不会自动停，要用户自己停。卡片右上角「⛶ 全屏」用 Fullscreen API 把这张卡片放大到整个屏幕，视频铺满全屏，详情和操作（起止滑块、定位按钮、AI 字幕）浮在右侧半透明条上，不用退出全屏也能微调。

每张卡片下方是一条区间滑块（起止两个手柄在同一条轨道上，中间高亮），拖动时播放器跟着实时跳转（B 站内嵌播放器每次跳转要整个重载 iframe，做了节流，不会拖一下重载一次）；「↺ 重置」还原到当前 `candidates.json` 里的值，「📋 复制新时间」把这张卡片的起止复制到剪贴板；顶部还有「📋 复制全部当前时间」一次性复制所有卡片。**这只是本地实时预览，不会自动写回 `candidates.json`**——预览页是本地 file:// 静态文件，浏览器 JS 没权限直接改磁盘文件，用户复制文本贴回对话后，由你手动更新 `candidates.json`（见下一节）。

用户想离线看精确片段时加 `--local`：默认 `--quality low` 下载 480P 图快，画质不够时可以 `--quality high` 走登录态下载最高画质（慢很多，按需用）。`--local` 下卡片改用本地 `<video>`，滑块窗口只能在原 `[start, end]` 内收缩，因为本地文件本身就只切出了这一段；滑块区右上角多一个「⏸ 暂停 / ▶ 播放」按钮，点视频本身也一样能切换，两者状态互相同步。不加 `--local` 时用的是 B 站官方 outside 内嵌播放器，画质由 B 站按未登录第三方内嵌的权限决定，往往到不了 1080P，这是平台限制，不是脚本的问题，需要看高清或精确核对边界就建议 `--local --quality high`；这个播放/暂停按钮只在 `--local` 模式下出现——iframe 是跨域文档，读不到它的播放状态，做不了可靠的切换按钮。

分 P 已经 `analyze` 过、`raw/pNN_subtitle.json` 存在时，卡片里滑块下方会带一块「AI 字幕」面板：按时间顺序列出滑块窗口内的每句字幕，片段内的加粗、窗口内但片段外的淡显，点一句直接跳到那句开头并自动播放（跟「定位开头/结尾」按钮不同，那两个按钮只定位不自动播）。`--local` 模式下 `<video>` 播放时还会跟着播放进度高亮当前那句并自动滚动到可见区域（B 站内嵌播放器拿不到播放进度，没有这个联动，只能点击跳转）。没跑过 `analyze` 或该 P 没有字幕文件时这块不显示，不会报错。

`--local` 模式下字幕面板下方还有一块「封面预览」：一张按 `cut` 会用的同一套逻辑（`cover_at` 字段 → 弹幕最密的一秒 → 兜底片段中点）挑出来的封面截图，配一个「🖼 用当前帧做封面 + 复制时间点」按钮。用户暂停在想要的画面（点视频、播放/暂停按钮、拖字幕都行）后点这个按钮，图片会立刻换成当前帧的预览（只是浏览器里画的 canvas 截图，不会写盘），同时把 `#id cover=时间点` 复制到剪贴板，跟改起止时间一样贴回对话，你把对应候选的 `cover_at` 字段（绝对秒数或时间字符串都行，跟 `start`/`end` 一个解析逻辑）写进 `candidates.json`，`cut` 时会优先用这个时间点截封面，没设置才退回默认逻辑。iframe 模式没有这块——跨域文档拿不到帧数据，`<canvas>` 画不出来。

### 5. 确认与微调

用户在对话里回复，例如「切 1、3、5，3 号结尾往后延 20 秒，5 号开头提前到 1:10:00」。你直接改 `candidates.json` 里对应候选的 `start` / `end`，被否掉的候选可以删掉或加 `"status": "rejected"`。改完不必重新预览，除非用户要求。

### 6. 切出成品

```
python3 bili_clip.py cut <工作目录> --ids 1,3,5
```

- 只下载命中的 P（最高画质，登录态一般是 1080P）到 `cache/`，同一 P 不重复下。
- 默认重编码（libx264 crf 18），起止精确到帧。用户赶时间可加 `--fast` 走流复制，起止会偏 1 到 2 秒。
- **用户要弹幕时加 `--danmaku`**，把片段内的弹幕烧进画面（B 站风格滚动弹幕，半屏、75% 不透明、1080p 下 57 号字，顶部 / 底部固定弹幕也支持）。默认不烧。想调样式用 `--danmaku-area 0.3`（占画面高度比例）、`--danmaku-opacity 0.6`、`--danmaku-size 40`（1080p 字号）。`--fast` 和弹幕互斥，加了 `--fast` 会自动不烧。
- 烧弹幕要带 libass 的 ffmpeg。脚本按「环境变量 `BILI_CLIP_FFMPEG` → Homebrew `ffmpeg-full` → PATH 里的 `ffmpeg`」的顺序找，都没有 libass 时会在下载视频之前就停下并给出安装命令，转告用户即可。
- 时间大头在下载分 P（每个 1 GB 上下），编码 4 分钟片段约一分钟，用户嫌慢时先说明这一点。
- 成品到 `clips/`，文件名 `序号_类型_标题_pN_起点-终点.mp4`，旁边同名 `.jpg` 是封面（取片段内弹幕最密的一秒，没弹幕取中点）。

**到这里任务完成。** 把成品路径列给用户即止，不要主动追问要不要发布。

### 7. 发布（可选，用户明确要求才做）

前提：`biliup` 在 PATH 里，且已 `biliup login` 扫码登录，把生成的 `cookies.json` 放到 `~/.config/bili-clip/biliup-cookies.json`（或当前目录）。没装时给出 https://github.com/biliup/biliup-rs/releases 下载链接和这两步。

`biliup login` 必须在终端里跑：菜单用方向键选（默认停在「短信登录」，按一次下箭头到「扫码登录」再回车），二维码同时会写到当前目录的 `qrcode.png`。你替用户操作时可以用 `pty` 起进程发按键，把 `qrcode.png` 用 `open` 或发文件给用户扫，登录成功后把当前目录生成的 `cookies.json` 挪到上面的路径。

```
python3 bili_clip.py publish <工作目录> --ids 1,3          # 只打印投稿计划
python3 bili_clip.py publish <工作目录> --ids 1,3 --yes    # 真正上传
```

不加 `--yes` 只输出计划：每条切片的标题、简介、标签、分区、封面、转载来源。把计划整理成表给用户看，**用户回复「发」之后才加 `--yes` 重跑**。用户想改标题或标签，改 `candidates.json` 里的 `publish_title` / `desc`，或用 `--tag` 追加标签。

默认值：转载类型并附原视频定位链接；简介自动追加主播和 `mentioned_streamers` 中已登记主播的 `space.bilibili.com/<uid>` 链接，标题、理由、摘录里出现的规范名或别名作为兜底识别，已在自定义 `desc` 里的同一 URL 不重复；分区跟原视频；标签为主播名 + 原视频前 3 个标签 + 「切片」；每个切片一个独立稿件。`--as-parts` 合并为一个稿件多 P，`--at "2026-09-07 20:00"` 定时发布（需距现在 4 小时以上）。

### 清理

`python3 bili_clip.py clean <工作目录>` 删掉 `cache/` 和 `preview/`，成品和字幕保留。

## 主播档案

路径 `~/.config/bili-clip/streamers/<主播名>.md`。分析前读，分析后更新。

首次遇到新主播：分析完这场后，根据本场内容起草档案，给用户看一眼确认再写入。模板：

```markdown
# <主播名>（uid）

## 称呼与别名
- 主播：陌陌 / 墨墨 / 苏墨墨（ASR 常写错的写法都列上）

## 常驻嘉宾
- 纯黑：联机队友，常迟到
- 巴老师：……

## 常见梗
- 「NPD」：调侃纯黑
- ……

## 投稿模板
- 分区：<tid> <名称>
- 固定标签：
- 简介模板：
```

每次分析结束后，把本场新出现的人名、别名、梗追加进去，直接写不必再问；投稿模板改动要问用户。主播本人的口头别名同时用 `streamers --alias` 写进登记表，`latest` 才能按别名找到她。

## 注意

- AI 字幕是 ASR 结果，人名和术语会写成同音字。对照主播档案纠正，摘录时可以在括号里标正确写法。
- 弹幕接口走分段 protobuf，能拿全量；但回放本身弹幕就少，密度信号弱时以字幕为主。
- 脚本按跨平台写法编写，实测只覆盖 macOS，Windows 未验证。
- 切片是二创，SKILL 不处理授权问题，主播是否允许切片由用户自己确认。
